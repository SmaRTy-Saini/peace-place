Normalization Layer for Inconsistent Healthcare Orders

Inbound orders arrived from multiple sources using inconsistent identifiers and naming conventions. The receiving laboratory workflow needed a dependable way to translate those differences into internal values.

The problem

Inbound orders arrived from multiple sources using inconsistent identifiers and naming conventions. The receiving laboratory workflow needed a dependable way to translate those differences into internal values.

What I built

  • Designed source-aware database crosswalks instead of hard-coding mappings into every interface.
  • Keyed mappings by source plus incoming value so the same external identifier could be interpreted correctly by context.
  • Added fallback matching when identifiers were missing or unreliable.
  • Separated payer normalization from order normalization so each could evolve independently.
  • Added controlled error handling for unmapped values rather than silently guessing.
  • Structured the approach so mappings could be maintained without rewriting interface logic.
Outcome

Inbound order processing became more deterministic and easier to maintain as new external sources were added.

Why this work matters

Normalization belongs in a maintainable data layer when external systems disagree about identifiers. That reduces duplicated interface code and makes exceptions visible rather than hidden.

How I approach similar projects

I start with the real production path: what enters the system, what decisions happen along the way, what should be observable, what can fail, and what the operator needs when something goes wrong. The implementation is then designed around reliability, maintainability, security, and support—not just getting one successful test through.
